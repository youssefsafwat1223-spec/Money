## 1. Scope, and what counts as evidence

### 1.1 Scope

This document covers the client (`app/`), both native layers (`app/ios/`, `app/android/`), the
Supabase Edge Functions and migrations (`supabase/`), the admin console (`admin/`), and the CI
gate (`tools/ci_gates.sh`, `.github/workflows/ci.yml`, `codemagic.yaml`). It is organised by the
eight OWASP MASVS v2 categories. It is an audit and a test plan. It proposes no implementation.

### 1.2 Honesty statement

**A checklist is not compliance.** Every row below is a statement about what this repository can
be shown to do, not a claim that the product is secure, private, or compliant with any regime.
Three specific limits apply:

1. **No network was used to produce this document.** Anything that can only be established
   against a live server, a live device, or a third-party console is marked `UNVERIFIED` or
   `BLOCKED BY EXTERNAL QA`, with the exact query or procedure that would settle it (§4, §5,
   and the `EXT-*` references throughout).
2. **There is no separate staging environment.** `docs/qa/MALI_MASTER_QA/10_TEST_STRATEGY.md:7`
   states that one Supabase project serves both real users and QA, and that safety comes from
   per-user feature-flag overrides plus dedicated QA identities. Every external item below
   therefore states explicitly whether it is *safely doable on the shared project with QA
   scoping* or *genuinely needs a new / throwaway project*. The merged register classifies 114
   of 120 external items as shared-project-safe and 6 as needing a separate project
   (`merged.json` `counts.external_shared_project_ok` / `external_needs_new_project`).
3. **Money does not currently move to or from Supabase in this build.** All three transport
   capability providers at `app/lib/data/sync/exact_transport_capability.dart:17-39` are
   `unknown`. Several findings below are therefore *latent* rather than *live*; that distinction
   is stated per row and must not be dropped when the capability is flipped.

### 1.3 Evidence grades

Exactly one status per invariant, from this vocabulary:

| Status | Means |
|---|---|
| **VERIFIED** | A real test exercises the runtime path — the production code executes and the assertion depends on its behaviour. |
| **TESTED WITH MOCKS** | A test exists and asserts something real, but a fake, an injected seam, or a source-text match stands in for the runtime path. |
| **UNVERIFIED** | The fact rests on source inspection only. No test, or only a test that cannot fail on this property. |
| **BLOCKED BY EXTERNAL QA** | Settling it requires a device, a live backend, or a third-party console that is unavailable offline. |

Two evidence anti-patterns recur and are called out by name wherever they appear:

- **A test that performs the behaviour it claims to verify.** `merged.json` flags 206 weak tests,
  with `performs_behavior_it_verifies` set on a substantial subset. Example:
  `app/test/core/privacy/diagnostics_consent_gate_test.dart` calls `DiagnosticsConsentGate.set`
  directly and then asserts the gate is set — it never taps the switch at
  `app/lib/features/settings/privacy_screen.dart:181-189` (PRIVACY-18). Such a test hides missing
  runtime orchestration.
- **A source-string guard asserted as proof of behaviour.** `app/test/features/ux_information_and_safety_test.dart:257-268`
  asserts that `app_database.dart` *contains the string* `PRAGMA cipher = 'sqlcipher';`. It would
  still pass if the throw were moved after `PRAGMA key`, or if the setup block were never invoked
  (SEC-55). The product's central at-rest claim is guarded by a grep living inside a UX-copy test
  file.

### 1.4 What this document does not establish

No claim is made here that the app is safe to ship, that any regulatory obligation is met, or
that the absence of a finding means the absence of a defect. 134 P0 and 338 P1 invariants exist
in the register; 526 are marked release-blocking; 614 of 1052 are `UNVERIFIED`
(`merged.json` `counts.by_status`).

authorization, or make recovery unsafe. **P1** = major user-visible financial/business
correctness failure. **P2** = non-critical functional/reliability. **P3** = cosmetic/minor UX.
Severities below are the merged register's post-verification grades.

## 3. Privacy leak-hunt plan

### 3.1 Test this first: the divergent-redaction finding

**RESOLVED in `c826d14b` + follow-up** (PRIVACY-14, PRIVACY-15, PRIVACY-36, SEC-12, SEC-33,
SEC-34, DISC-145). Recorded here in full because the shape of the defect is the finding: four
independent copies existed, and the two that disagreed most were the two on the path that reaches
an **off-device AI service**.

What was wrong, and what it cost:

| Implementation | Was missing | Reaches |
|---|---|---|
| Dart `app/lib/engine/privacy/sms_sanitizer.dart` | Arabic-Indic digits; case-sensitive IBAN | In-app capture path |
| Swift `app/ios/BankMessageShortcuts/BankMessageShortcuts.swift` | **IBAN, OTP**, Arabic-Indic digits — and a `try?` + `continue` that silently skipped any rule that failed to compile | **The iOS App Intent's direct POST to `process-ios-sms`** |
| Deno `process-ios-sms/index.ts` | **IBAN, OTP**, Arabic-Indic digits | The Gemini prompt and `processed_captures.sanitized_text` |
| Deno `bank-discovery/index.ts` | **IBAN, OTP**, Arabic-Indic digits — and its `containsUnsafeRawData` fail-closed gate was digits-only, so an IBAN passed the gate too | The bank-identification Gemini prompt |
| Deno `parse-sms/index.ts` | Arabic-Indic digits | The in-app relay path |

The IBAN gap was never theoretical: `\b\d{10,20}\b` cannot match
`SA0380000000608010167519`, because there is no word boundary between `SA` and the digits.

How it is closed:

- The three server copies now share one floor, `supabase/functions/_shared/sms_redaction.ts`.
  Callers add rules on top (parse-sms keeps beneficiary stripping, bank-discovery keeps its
  masked-account cues); they cannot subtract.
- Arabic-Indic and extended Arabic-Indic digits are matched **in place** rather than normalised
  first, because the proof layer compares model output against spans of the very string that was
  sent and `sanitization_edit_map.dart` records where each character went. `\b` is defined over
  `[A-Za-z0-9_]` and does not treat U+0660 as a word character, so it was replaced by the same
  assertion widened to cover those digits — exactly equivalent to `\b` on ASCII input.
- The Swift copy fails **closed**: a rule that will not compile now throws
  `BackendCaptureError.sanitizerUnavailable` instead of being skipped. This was a live fail-open —
  the first Arabic-Indic attempt used Swift's `\u{...}` escape where ICU wants `\uFFFF`, every
  rule failed to compile, and the harness showed the raw SMS passing through untouched.
- One corpus is pinned in all three places — `app/test/engine/sms_sanitizer_test.dart`,
  `supabase/functions/_shared/sms_redaction_test.ts`, and `app/tool/verify_swift_sanitizer.sh`,
  which lifts `sanitize()` out of the shipped Swift source verbatim so the code under test is the
  code that ships. Each carries the IBAN case that used to leak, the Arabic-Indic cases, the
  lower-case IBAN, and — because cue-anchoring is why OTP redaction is safe at all — the amounts
  that must survive untouched.

Still open on this surface: **SEC-33/SEC-34 (P1)** — `process-ios-sms` re-sanitizes only
`sanitizedText`; `rawText` is taken verbatim from the body and copied into `parsed.rawMessage`.
Both shipping clients sanitize before sending, so this is a missing defence-in-depth layer rather
than a live leak, but it is the layer `07_SECURITY.md:58` says must be preserved.

### 3.2 The marker approach

Seed exactly one synthetic bank message per platform whose body contains a unique, greppable
marker plus one instance of every PII class the sanitizers claim to handle:

```
QA_SECRET_BANK_MESSAGE_<random>
  IBAN (uppercase):        SA0380000000608010167519
  IBAN (lowercase):        sa0380000000608010167519          # PRIVACY-36
  Card:                    4417 8833 2211 0099
  Card (Arabic-Indic):     ٤٤١٧٨٨٣٣٢٢١١٠٠٩٩                  # PRIVACY-14
  Account (10-20 digits):  12345678901234
  OTP with an amount:      رمز التحقق 481902 لعملية بمبلغ 1500 ر.س   # SEC-48, PRIVACY-14
  Phone (SA / EG / intl):  0551234567 / 01012345678 / +447700900123
  Beneficiary + greeting:  حوالة إلى محمد عبدالله
  Integer amount:          خصم 1500 ر.س                       # PRIVACY-66
  Bare last-4:             البطاقة 4417                        # PRIVACY-67
  Merchant:                QA-CANARY-DO-NOT-MAP                # safe canary for EXT-031
```

`<random>` must be freshly generated per run so a stale hit is distinguishable. Every search
target below is then a grep for `QA_SECRET_BANK_MESSAGE_` **plus** a grep for each raw PII value
independently — the marker proves the message reached the sink; the PII values prove what
survived redaction.

## 4. Cloud-OFF / AI-OFF verification

### 4.1 Why code-reading is insufficient here

"Cloud OFF verified" is a claim about **observed network behaviour**. The repository contains no
tooling capable of observing it (PRIVACY-53): no `HttpOverrides` installation anywhere in
`app/lib`, `app/test` or `app/integration_test`; no proxy or pcap harness; and every consent test
injects a fake into exactly one service. `app/integration_test/post_auth_journeys_test.dart:217-242`
turns consent **ON** through the real UI and never asserts an OFF state.

Three specific things can only be settled on the wire:

1. **Native-layer egress no Dart harness can see** — the Sentry native SDK's crash envelopes
   (PRIVACY-38), release-health session envelopes (PRIVACY-39), the AdMob/UMP SDK (PRIVACY-60),
   and the iOS App Intent's `URLSession` POST at
   `app/ios/BankMessageShortcuts/BankMessageShortcuts.swift:496-525` (PRIVACY-64).
2. **Calls the static guard structurally cannot match** — the 17 files listed in §2.4, two of
   which (`planning_push_service.dart:122`, `supabase_planning_support.dart:38`) no quoted-literal
   regex would catch at any formatting.
3. **Whether the server's own gates actually fire on the deployed revision** — config.toml is only
   honoured by the CLI at deploy time (EXT-030).

### 4.2 Procedure, given there is no staging environment

Everything below runs against the **shared project**. Per
`docs/qa/MALI_MASTER_QA/10_TEST_STRATEGY.md:7`, safety comes from a dedicated QA identity, a QA
install id, and per-user feature-flag overrides — the same mechanism whose soundness rests on
`feature_flag_overrides` having no client write policy (AUTH-22, untested; see §5.2).

**Step 1 — Proxied device run (EXT-017, shared-project safe).**
Install the `QIRSH_BUNDLE_SUFFIX` QA build on a device behind an HTTPS-intercepting proxy with the
device CA trusted. Sign in as a dedicated QA identity. Leave **both** consent switches at `unset`.
Then: cold start → open every tab → add a manual transaction → trigger a capture via the Shortcut
→ background/foreground three times → force a crash. Record every host and path.

- **Expected allowlist:** `<project>.supabase.co/functions/v1/catalog-*` and
  `<project>.supabase.co/auth/v1/*`.
- **Any of the following is a failure:** `o*.ingest.sentry.io`, `googleads.g.doubleclick.net`,
  `img.logo.dev`, `/rest/v1/profiles`, `/rest/v1/user_*`, `/rest/v1/rpc/record_metric`,
  `/rest/v1/rpc/record_engagement_event`, `/functions/v1/enrich-merchant`.
- Repeat with consent **accepted**, then **revoked mid-session**.

**Step 2 — Sentry, which needs a separate DSN, not a separate Supabase project.**
Sentry is third-party SaaS, so no QA scoping protects it. Build the QA bundle with its own
`SENTRY_DSN` (and a distinct `dist`) so QA events cannot pollute production release health. Then:

- **EXT-111** — launch with consent unset and watch for `POST /api/<id>/envelope/` carrying an item
  of type `session` (PRIVACY-39). *Settle by code first:* setting
  `options.enableAutoSessionTracking = false` at `app/lib/main.dart:32-63` makes the question moot.
- **EXT-112** — QA identity with `cloud_processing_enabled = false`, trigger a **native** crash
  (not a Dart exception), relaunch, and check the Sentry project for an event with that
  release/dist (PRIVACY-38).
- **EXT-113** — grant consent → force a native crash → **revoke consent before relaunching** →
  relaunch → check both the proxy log and the Sentry issue stream for a new event at that
  timestamp. This is the documented Dart-boundary bypass at
  `app/lib/core/observability/telemetry_sanitizer.dart:21-26` (DISC-143).

**Step 3 — Server-side consent enforcement (EXT-031, shared-project safe, edge probe).**
With a QA user JWT and **no** `capture_devices` row:

```
curl -s -o /dev/null -w '%{http_code}' -X POST \
  "$SUPABASE_URL/functions/v1/enrich-merchant" \
  -H "Authorization: Bearer $QA_JWT" -H 'Content-Type: application/json' \
  -d '{"merchant_name":"QA-CANARY-DO-NOT-MAP","country_code":"SA","write":false,

```

Expect **403**. Repeat for `parse-sms`, `bank-discovery`, `prepare-affiliate-click`,
`affiliate-click-status` (PRIVACY-22).

> **CRITICAL SAFETY (EXT-045):** pass `write:false`. With `write:true` — the client's default — a
> success would UPSERT into the **global** `merchant_keywords` catalog that every user syncs. That
> is production catalog pollution, not test data. If a write path must be exercised, use the canary
> name above and clean up: `DELETE FROM public.merchant_keywords WHERE keyword ILIKE 'QA-CANARY%';`
> This single case is the **only** item in the whole external set that would otherwise need a
> separate project.

**Step 4 — AI-OFF specifically.**
Set `ai_consent_granted = true` and `cloud_processing_enabled = false` for the QA identity, then:

### 5.3 The finding that makes all of §5.1 CI-invisible

**Credential-gated suites under `supabase/tests` self-skip, and CI supplies no credentials.**

- The mechanism is node's `{ skip }` option resolved from `process.env`:
  `supabase/tests/coupons_rls_live_node_test.mjs:14-20`, `revision_cas_node_test.mjs:10-14`,
  `engagement_events_node_test.mjs:9-15`, `coupon_metrics_live_node_test.mjs:13-19`,
  `remote_backup_live_node_test.mjs:12-19`, and nine more — **14 of 33 `.mjs` files read
  credentials**. On the Deno side, two cases are gated by `ignore: !HAS_CREDS`
  (`supabase/functions/_shared/ai_endpoint_realbackend_test.ts:15`).
- `.github/workflows/ci.yml:1-59` has **no `env:` and no `secrets:` block at all**, so all 14 plus
  both Deno cases skip on **every** PR.
- `tools/test_skip_manifest.json:22,30,38,46,60,68` carries a `mustRunWhenPrereq` rule, but it only
  bites once credentials exist, and nothing in the repository ever supplies them.
- The gate's own contract test asserts *what* `ci.yml` runs
  (`supabase/tests/ci_gates_contract_node_test.mjs:55-60`), never *what it supplies*. **No test
  observes that the workflow provides no credentials, so the permanent-skip condition is invisible
  to the suite.**
- Two further blind spots: `tools/ci_gates.sh:156` globs `supabase/tests/*.mjs`, so the two `.sql`
  isolation scripts are executed by nothing, and two `*_live_harness.mjs` operator tools land in
  the "node tests skipped" count at `ci_gates.sh:248` and read as ordinary credential-gated tests.

- On the Dart side, nine of ten on-device harness files `return` green when QA credentials are
  absent; only `app/integration_test/demo_seed_test.dart:85-87` calls `fail()`.

**Consequence:** every N-row above whose only coverage is a credential-gated live test is, in
practice, **untested in CI** — and the gate reports green. Discharging this needs either a
credentialed job or a **recorded, dated live run of the 14 credential-gated files against the
shared project under QA identities, attached to each release**, plus an architecture test asserting
that `ci.yml` either supplies the credentials or explicitly documents the tier as deferred.

**Path:** `/Users/luciq/Documents/Money/supabase/rollback/backups/user_transactions_pre_0022_backup.json`
**Size:** 5097 bytes. **Modified:** 2026-07-12.

### 6.1 Exposure scope, stated precisely

| Question | Answer | Evidence |
|---|---|---|
| Is it ignored by git? | Yes | `git check-ignore -v` resolves to `supabase/.gitignore:6` (`rollback/backups/`), whose comment at `:5` reads "Contains real production rows exported for migration safety — never commit" |

| Therefore the exposure is… | **Local disk only.** The working copy on this machine, plus any machine-level backup of it. It has never been distributed through the repository, a remote, a fork, or a clone | The three rows above |

This is deliberately narrower than "a real-user data leak". Nothing here establishes that the file
left this machine. Equally, nothing establishes that it did not — a machine backup, a sync client,
or a shared-drive mirror would carry it, and none of those is observable from the repository.

### 6.2 Gaps

- **The ignore rule is trusted, not enforced.** No CI or pre-commit gate fails if a file under
  `supabase/rollback/backups/` ever becomes tracked. The protection is one `git add -f` away from
  being defeated.
- **No retention or expiry.** The export has sat since 2026-07-12 with no deletion date and no
  documented policy for pre-migration data exports.
- **Severity:** P2 as graded in the register — real user financial rows at rest on a developer
  workstation, with no cross-user boundary crossed and no distribution path established.

### 6.3 Recommended verification (no code change proposed)

1. An operator decision on whether the file is still needed for the 0022 rollback path; if not, a
   dated deletion record.
2. A repository check — not written here — that would fail if any path under
   `supabase/rollback/backups/` becomes tracked.
3. Scan any developer-machine backup destination for the same filename, since that is the only
   distribution channel the git evidence leaves open.
