| **Why it blocks** | Two ways at once: (a) Apple and Google both require a working public privacy-policy URL, and (b) it is a live product defect — the in-app Privacy screen opens a dead link in the shipping build. |

**Per OD-06, engineering does NOT wait on a domain purchase.** The plan is:

1. **Claude prepares** the Privacy Policy and Terms as deployable static artifacts, plus URL
   plumbing so the destination is configuration, not a hardcoded constant. *(Sequenced after the
   Phase-D consent work — see the note below.)*
2. **Owner performs** exactly one step: publish those artifacts to any stable public HTTPS host
   (a free static host is acceptable per OD-06) and provide the two resulting URLs.
3. **Claude wires** the URLs through configuration and re-verifies.

> **Deliberate sequencing note.** The policy text is NOT being written yet, on purpose. The whole
> point of a privacy policy is that it describes what the software actually does — and C-3/F-025 is
> still open, meaning the consent switch currently promises more than it enforces (see
> `QIRSH_MASTER_PLAN_V2.md` §9.2). Writing the policy before that fix would encode a claim that is
> untrue on the day it is published. The policy is therefore authored **after** Phase D, against
> enforced behaviour, not intended behaviour.

## 6. CRITICAL PATH

```
partition tree ✅
   → stop-the-bleeding criticals (C-1 ✅, C-2 ✅, C-2a ✅, C-9 ⏳)
   → environment truth (DF-002 ✅ source) ──────────┐
   → privacy authority (Phase D)                     │ these unblock a reproducible
   → data integrity (Phase E)                        │ staging environment, which
   → capability activation prep (Phase F)  ←─────────┘ every remote proof depends on
   → [OWNER] staging project + authorisation
   → migration + function rehearsal on staging
   → [OWNER] Distribution cert / ASC record
   → internal build → device QA → beta → staged rollout → production
```

**Runs in parallel from now, not at the end:** every APPLE, GOOGLE, and LEGAL/HOSTING row above.
Those are the longest poles and none of them depend on the remaining code work.

**Staged rollout reality check:** a *binary-level* phased release (App Store phased / Play staged)
works today. *Feature-level* kill switches do **not** — only 3 of 26 flags have a live consumer, and
the server resolver ignores `rollout_percent` entirely (C-10). Do not plan a rollout that assumes a
per-feature kill switch until C-10 lands.
