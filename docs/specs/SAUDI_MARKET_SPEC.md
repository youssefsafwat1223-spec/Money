# ملحق السوق السعودي (Saudi Launch Spec)

> ملحق تنفيذي لـ docs/specs/PRODUCT_SPEC.md — يخصّص المنتج لسوق الإطلاق الأول: **المملكة العربية السعودية**.
> ⚠️ كل قوالب الرسائل أدناه **تمثيلية (illustrative)** ويجب التحقق منها مقابل corpus رسائل حقيقية قبل الاعتماد.

---

## 1. لماذا السعودية أولاً (ملاءمة السوق)

| العامل | الأثر على المنتج |
|---|---|
| اختراق بطاقات/مدفوعات رقمية مرتفع (mada, Apple Pay) | كثافة عمليات → رسائل بنكية غزيرة → قيمة فورية |
| حصة iOS مرتفعة نسبياً | يجب أن يكون مسار Share/Shortcut/Paste درجة أولى منذ اليوم الأول |
| عملة واحدة (SAR) | يبسّط الـ Parser والتقارير (لا تحويل عملات في MVP) |
| لغة مختلطة في الرسائل (عربي + إنجليزي) | الـ Parser يجب أن يدعم locale مزدوج في نفس الرسالة |
| وعي مرتفع بالادخار/الأهداف المالية | التلعيب وأهداف الادخار تلقى صدى |

## 2. العملة والتنسيق المحلي (Locale)

```
currency_code   : SAR
symbol          : ﷼ / "ريال" / "ر.س"  (الرسائل تستخدم الثلاثة)
decimal_places  : 2
grouping        : 1,240.50   (فاصلة آلاف، نقطة عشرية)
locale (app)    : ar-SA  (RTL، أرقام عربية-غربية 0-9 افتراضياً)
date formats    : هجري + ميلادي — الرسائل قد تستخدم أيهما → ندعم الاثنين
time zone       : Asia/Riyadh (UTC+3)
```
**ملاحظة أرقام:** بعض الرسائل تستخدم الأرقام الهندية (٠١٢٣٤٥٦٧٨٩). الـ Parser يجب أن **يطبّع** الأرقام الهندية → الغربية قبل الاستخراج.

**ملاحظة تواريخ:** بعض البنوك ترسل تاريخاً هجرياً. نخزّن دائماً ميلادي (UTC) في DB، ونحوّل عند العرض.

## 3. البنوك والمحافظ المستهدفة للإطلاق (Bank Profiles)

نبدأ بأكبر مزوّدين تغطيةً. كل واحد = `bank_key` في جدول `parsing_rules`.

| # | الجهة | bank_key | النوع | أولوية |
|---|---|---|---|---|
| 1 | الأهلي السعودي (SNB) | `snb` | بنك | P0 |
| 2 | الراجحي | `alrajhi` | بنك | P0 |
| 3 | بنك الرياض | `riyad` | بنك | P0 |
| 4 | البنك السعودي الأول (SAB) | `sab` | بنك | P1 |
| 5 | الإنماء | `alinma` | بنك | P1 |
| 6 | البنك العربي الوطني (anb) | `anb` | بنك | P1 |
| 7 | STC Pay | `stcpay` | محفظة | P0 |
| 8 | urpay / barq / محافظ ناشئة | `wallet_*` | محفظة | P2 |
| 9 | mada (شبكة) | يظهر داخل رسائل البنوك | — | يُعالج كـ source=card |

**P0 = إلزامي للـ MVP.** P1 سريعاً بعده. P2 لاحقاً.

> إجراء مطلوب من الفريق: جمع **عينات رسائل حقيقية مجهّلة** لكل bank_key (≥30 رسالة متنوعة: دفع/سحب/تحويل/استرداد/راتب). هذا أهم أصل في المشروع.

## 4. أنماط الرسائل التمثيلية (Illustrative Templates)

> هذه قوالب نمطية شائعة للاسترشاد ببناء الـ regex — **تُستبدل بأنماط حقيقية بعد جمع الـ corpus.**

### 4.1 دفع ببطاقة (عربي)
```
عملية شراء
بطاقة:مدى;****4521
مبلغ:SAR 45.00
لدى:BURGER BOUTIQUE
في:2026-04-08 12:45
الرصيد:SAR 2,310.50
```
الاستخراج المتوقع:
```
type=payment, source=card, card_last4=4521,
amount=45.00, currency=SAR, merchant="BURGER BOUTIQUE",
occurred_at=2026-04-08T12:45+03:00, balance_after=2310.50
```

### 4.2 دفع (إنجليزي مختلط)
```
Purchase
Card ending 4521
Amount SAR 45.00
At BURGER BOUTIQUE
2026-04-08 12:45
```

### 4.3 سحب نقدي (ATM)
```
سحب نقدي
مبلغ:SAR 500.00
من جهاز الصراف
بطاقة:****4521
الرصيد:SAR 1,810.50
```
→ `type=withdrawal, category=سحب نقدي`

### 4.4 تحويل
```
تحويل صادر
مبلغ:SAR 300.00
إلى:MOHAMMED A
المرجع:...
```
→ `type=transfer, category=تحويلات`

### 4.5 إيداع راتب / دخل
```
إيداع راتب
مبلغ:SAR 9,500.00
الرصيد:SAR 11,310.50
```
→ `type=income, category=دخل` (يُستثنى من حسابات الميزانية، يدخل في حساب التوفير)

### 4.6 استرداد (Refund)
```
استرداد مبلغ
مبلغ:SAR 45.00
من:BURGER BOUTIQUE
```
→ `type=refund` (يُعكَس على ميزانية التصنيف الأصلي إن أمكن)

### 4.7 STC Pay
```
تم الدفع بنجاح
المبلغ: 30.00 ريال
لدى: JARIR
رقم العملية: ...
```
→ `source=wallet, merchant="JARIR", category=تسوق`

## 5. استراتيجية الـ Parser للسعودية (خطوات التطبيع)

```
1) Pre-normalize:
   - أرقام هندية → غربية (٠-٩ → 0-9)
   - توحيد رمز العملة: "ريال" | "ر.س" | "﷼" | "SAR" → SAR
   - إزالة tatweel (ـ) ومسافات زائدة
   - توحيد فواصل: thousands ',' / decimal '.'

2) Detect bank_key:
   - بصمة المُرسِل (sender id) + كلمات مفتاحية في النص

3) Apply bank profile rules (regex per field) بالترتيب حسب priority

4) Extract fields:
   amount, currency, merchant(raw), type, source, card_last4,
   occurred_at, balance_after

5) Classify type:
   شراء/عملية شراء/Purchase → payment
   سحب/صراف/ATM            → withdrawal
   تحويل                    → transfer
   استرداد/Refund           → refund
   راتب/إيداع               → income

6) Confidence score:
   كل الحقول الأساسية موجودة → high → تصنيف صامت ممكن
   amount مفقود/مشبوه       → low → status=pending + اطلب تأكيد
```

### عتبات القرار
```
parse_confidence >= 0.85  → احفظ تلقائياً (إن المتجر معروف) + إشعار خفيف
0.6 <= conf < 0.85        → احفظ + اطلب تأكيد سريع
conf < 0.6                → status=pending، لا تحدّث الميزانية حتى يؤكّد
```

## 7. اعتبارات تنظيمية وامتثال (Compliance — السعودية)

| البند | الإجراء |
|---|---|
| **Google Play SMS Policy** | تطبيقات تتبّع المصاريف عبر SMS مسموحة كـ "financial management" لكن تتطلب **Permissions Declaration** واضحة + إثبات أن SMS وظيفة جوهرية. **يجب التحقق والتجهيز قبل البناء.** |
| **PDPL (نظام حماية البيانات الشخصية السعودي)** | بنية on-device تخدمنا بقوة: لا نقل بيانات شخصية لخارج الجهاز → مخاطر امتثال أدنى. سياسة خصوصية بالعربية إلزامية. |
| **SAMA / بيانات مالية** | لا نتصل بأنظمة بنكية ولا نقرأ حسابات عبر API — نقرأ فقط رسائل وصلت لجهاز المستخدم بموافقته. هذا يبقينا خارج نطاق ترخيص fintech في MVP. *(يُراجع قانونياً قبل الإطلاق.)* |
| **Apple App Store** | iOS لا SMS — نعتمد Share Extension/Shortcut. متوافق مع سياسات Apple. |
| **اللغة** | سياسة خصوصية + شروط استخدام بالعربية (والإنجليزية اختياري). |

## 8. تخصيص التجربة للسعودية

- **النبرة:** عربية فصحى مبسّطة قريبة من اللهجة (ودّية، ليست رسمية جافة). تحية: «صباح الخير» / «مساء الخير».
- **التاريخ:** عرض ميلادي افتراضي مع خيار هجري في الإعدادات.
- **الخزنة 3D:** خزنة محايدة ثقافياً (لا piggy/كحول/رموز غير مناسبة) — متوافق مع متطلبات السوق.
- **الأهداف الشائعة (seed goals):** «رحلة صيف»، «شراء سيارة»، «الزواج»، «صندوق طوارئ»، «الحج/العمرة».
- **التصنيفات الحسّاسة:** «هدايا»، «أطفال»، «منزل» مفيدة للأسر السعودية.
- **الاشتراكات الشائعة للكشف:** Shahid, Netflix, STC, Jawwy TV, OSN, iCloud, Spotify.

## 9. أول حزمة عمل للمطورين (Saudi Sprint 0–1)

**Sprint 0 — تأسيس (لا UI):**
1. ✅ التحقق من Google Play SMS Declaration (blocker).
2. ✅ جمع corpus رسائل حقيقية لـ P0 (snb, alrajhi, riyad, stcpay).
3. ✅ إعداد schema + seed (categories + merchant_map + goals).

**Sprint 1 — المحرك:**
4. Normalizer (أرقام هندية، عملة، تواريخ هجري/ميلادي).
5. Bank profiles لـ P0 + golden tests (هدف ≥90% على الـ corpus).
6. Categorization Engine + بذور المتاجر.
7. مسار end-to-end: لصق رسالة → parse → confirm → حفظ → Dashboard. (يثبت الـ Aha)

## 10. أسئلة سعودية محدّدة تحتاج إجابتك

1. هل نبدأ بـ **4 جهات P0** (SNB, الراجحي, الرياض, STC Pay) أم نوسّع للـ P1 فوراً؟
2. هل تملك وصولاً لعينات رسائل حقيقية من هذه البنوك (حساباتك/فريقك) لبناء الـ corpus؟
3. التاريخ الافتراضي في الواجهة: ميلادي أم هجري؟
4. هل نضيف «صندوق طوارئ» و«الحج/العمرة» كأهداف مقترحة جاهزة؟
5. الثيم الأساسي عند الإطلاق: Dark أم Light؟
