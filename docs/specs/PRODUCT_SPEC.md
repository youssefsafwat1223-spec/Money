# تقرير المنتج الكامل — تطبيق تتبع المصاريف التلقائي (Arabic-first)

> وثيقة تأسيسية واحدة (Single Source of Truth) لفريق Product + Design + Engineering.
> الحالة: Pre-Figma / Pre-Code. الجمهور: مصممون ومطورون حقيقيون.
> آخر تحديث: 2026-06-09.

---

## 0. الملخص التنفيذي (Executive Summary)

تطبيق موبايل عربي (Arabic-first / RTL) يحوّل رسائل البنك والمحافظ الإلكترونية إلى سجل مصاريف مصنّف تلقائياً، بدون إدخال يدوي ممل. القيمة الأساسية: **"لا تكتب مصروفاتك. نحن نفهمها لك."** التجربة مبنية على التلعيب (Streak / XP / خزنة 3D / أهداف ادخار) بحيث يصبح التوفير عادة يومية ممتعة.

**التمايز الجوهري:** المعالجة المالية كلها **on-device**. لا سيرفر للبيانات المالية. هذا في آن واحد ميزة خصوصية وميزة تقنية (تكلفة تشغيل شبه صفرية، لا التزامات تخزين مالي).

**الأسواق:** السعودية، مصر، العراق، الخليج. تعدد عملات وتعدد لهجات رسائل بنكية.

**القرار المعماري الأهم:** عزل **Parser Engine** و**Categorization Engine** عن طبقة الواجهة (UI) تماماً، بحيث يمكن اختبارهما بمعزل وتطويرهما كـ rule-based قابل للتوسعة دون لمس الواجهة.

## 1. فهم الفكرة (Product Understanding)

الفكرة ليست "تطبيق محاسبة". هي **مساعد مالي سلبي (passive finance companion)** يعمل في الخلفية ويظهر فقط عند الحاجة (تأكيد عملية، تنبيه ميزانية، احتفال إنجاز).

ثلاث ركائز:

1. **Zero-effort capture** — البيانات تدخل تلقائياً من قناة موجودة أصلاً (رسائل البنك).
2. **Intelligence on top** — تصنيف، insights، كشف اشتراكات، تنبيهات استباقية.
3. **Behavioral motivation** — تلعيب يحوّل الالتزام المالي من "واجب" إلى "لعبة".

ما يجب أن **لا** يكونه التطبيق: Excel، Dashboard مزدحم بالـ charts، أداة جلد ذاتي مالي. الشعور المستهدف: *خفيف، premium، محفّز، آمن*.

## 2. المشكلة والقيمة (Problem & Value)

| البُعد | الوصف |
|---|---|
| **المشكلة الحقيقية** | ليست نقص الرغبة في التنظيم، بل أن الإدخال اليدوي عبء يقتل الاستمرارية. تطبيقات المصاريف التقليدية تُهجر خلال أسابيع. |
| **سبب الفشل** | احتكاك (friction) عالٍ + لا تحفيز + شكل محاسبي بارد. |
| **حلّنا** | إلغاء الإدخال اليدوي (capture تلقائي) + تحفيز سلوكي (gamification) + بساطة بصرية premium. |
| **القيمة للمستخدم** | "أعرف أين تذهب فلوسي بدون أي مجهود، وأشعر أني أتقدّم." |
| **القيمة التجارية** | قاعدة مستخدمين عالية الالتزام (daily active) + بيانات سلوك صرف (on-device) تتيح عروض/كوبونات سياقية لاحقاً. |

**معيار النجاح للمنتج (North Star Metric):** عدد العمليات الملتقطة والمؤكَّدة تلقائياً لكل مستخدم نشط أسبوعياً (Captured & Confirmed Transactions / WAU). يقيس أن المحرك يعمل وأن المستخدم يثق به.

## 3. المستخدم المستهدف (Target User)

- **العمر:** 20–40.
- **السلوك المالي:** يستخدم بطاقة بنكية/محفظة إلكترونية بكثافة، يصله SMS من البنك عند كل عملية.
- **المستوى التقني:** متوسط — يستخدم تطبيقات يومياً لكنه لا يحب الإعدادات المعقدة.
- **الدافع:** يريد التوفير أو ضبط الصرف لكنه "ما يعرف يبدأ"، أو جرّب تطبيقات وفشل في الالتزام.
- **الجهاز:** Android أغلبية في مصر/العراق، iOS حضور قوي في الخليج/السعودية → **المنصتان إلزاميتان**، لكن Android يحمل الميزة الأقوى (SMS auto-capture).

## 5. رحلة المستخدم (User Journey — مستوى عالٍ)

| المرحلة | الحالة الذهنية | نقطة الاحتكاك | كيف نكسب |
|---|---|---|---|
| الاكتشاف | "أبي أنظّم فلوسي بس بدون تعب" | عدم الثقة في الصلاحيات | رسالة خصوصية واضحة + on-device |
| Onboarding | فضول حذر | طلب صلاحية SMS مخيف | شرح القيمة *قبل* طلب الصلاحية |
| أول قيمة (Aha) | "وااو لقطها لحالها!" | إن فشل أول parse | نضمن أول عملية تُلتقط (عيّنة/لصق موجّه) |
| الاستخدام اليومي | عادة | الملل | Streak + Insights + احتفالات صغيرة |
| الاحتفاظ | فخر | فقدان السبب | أهداف ادخار + خزنة تمتلئ + تقارير أسبوعية |

**لحظة الـ Aha المستهدفة:** أول رسالة بنك تُلتقط وتُصنّف صحيحاً خلال أول 24 ساعة. كل الـ onboarding يُبنى لإيصال المستخدم لها بأسرع ما يمكن.

## 6. تدفقات المستخدم (User Flows — تفصيلي)

### 6.1 First-run
```
Splash
 → Intro 1 (المشكلة) → Intro 2 (الحل: capture تلقائي) → Intro 3 (التلعيب/الخزنة)
 → اختيار الدولة + العملة
 → شاشة الخصوصية (on-device, لا رفع بيانات)
 → اختيار طريقة الإدخال:
      Android → طلب صلاحية SMS (مع شرح + زر "لاحقاً")
      iOS     → شرح Share Extension + Shortcut + زر "جرّب الآن بلصق رسالة"
 → (اختياري) أول ميزانية أو "تخطّي"
 → Dashboard (فارغ ذكي: يدعو لالتقاط/لصق أول عملية)
```

### 6.2 عملية جديدة (Auto-capture)
```
وصول SMS بنك (Android BroadcastReceiver)
 → Parser Engine يستخرج الحقول
 → نجح الاستخراج؟
     لا  → حفظ كـ "غير مؤكدة" + إشعار "راجع عملية"
     نعم → المتجر معروف في merchant_category_map؟
              نعم → تصنيف تلقائي + حفظ صامت + إشعار خفيف + تحديث Budget/Streak/XP
              لا  → إشعار "أكّد عملية جديدة" → شاشة Confirm
 → تحديث Insights / كشف اشتراك محتمل
```

### 6.3 تصحيح تصنيف
```
فتح Transaction Details → تعديل التصنيف
 → سؤال: "طبّق على هذه العملية فقط؟ أم كل العمليات القادمة من نفس المتجر؟"
     فقط هذه → تحديث transaction.category_id
     الكل    → upsert في merchant_category_map (is_user_confirmed = true)
 → (لاحقاً) إعادة تصنيف ذكية للعمليات السابقة من نفس المتجر (اختياري بسؤال)
```

### 6.4 إنشاء هدف
```
Goals → Add Goal → الاسم + المبلغ المستهدف + المدة (deadline)
 → حساب المبلغ الموصى به أسبوعياً/شهرياً
 → إنشاء Vault مرتبط بالهدف → عرض Progress 0%
```

### 6.5 لصق يدوي (كل المنصات)
```
Manual Paste → لصق نص الرسالة → Parser يعرض المعاينة (preview قابلة للتعديل)
 → تأكيد → حفظ كعملية عادية
```

## 8. نطاق الـ MVP (MVP Scope)

**الهدف:** إثبات أن المحرك يلتقط ويصنّف بدقة كافية، وأن التلعيب يخلق عادة يومية.

**يشمل:** F1–F13 (كل الـ Must).

**حدود واضحة للـ MVP:**
- بنوك مدعومة: نبدأ بأكبر 5–8 بنوك/محافظ في أسواق الإطلاق فقط (تُحدَّد بعينات رسائل حقيقية).
- العملات: SAR, EGP, IQD, AED, + الأساسيات الخليجية.
- **مصادقة أثناء onboarding** (Google/Apple/OTP). **Backup مشفّر E2E اختياري ومطفأ افتراضياً** (يُفعّل من الإعدادات).
- بدون backup: لا تغادر أي بيانات مالية الجهاز. مع backup: فقط blob مشفّر E2E لا نملك مفتاحه.
- backend في MVP: auth + backup blob (للمفعّلين فقط) + مقاييس مجهولة + parsing_rules config.
- لوحة أدمن ويب بمقاييس مجمّعة مجهولة فقط.
- لا إعلانات إطلاقاً.
- التقارير في MVP = نسخة مبسّطة جداً (أو تُؤجَّل لأول تحديث).

**معيار خروج الـ MVP (Definition of Done):**
- دقة الـ Parser ≥ 90% على عينة الرسائل المدعومة.
- دقة التصنيف التلقائي ≥ 80% بعد أول أسبوع استخدام.
- مستخدم يصل لـ Aha (أول عملية مؤكّدة) خلال أول جلسة.

## 10. اتجاه الـ UI/UX (Direction)

- **Arabic-first, RTL by default** — كل layout يُصمَّم RTL أصالةً لا انعكاساً.
- **Calm premium** — مساحات بيضاء، عناصر قليلة لكل شاشة، حركة هادفة لا زخرفية.
- **Emotion before data** — كل شاشة تبدأ بشعور/تحفيز ثم تفصيل.
- **One primary action per screen** — وضوح في الـ hierarchy.
- **Celebration, not pressure** — التلعيب يحتفل بالإنجاز ولا يعاقب على التقصير.
- **مرجعيات إلهام (لا نسخ):** Apple Wallet (البطاقات/العمق)، Apple Fitness (الحلقات/التحفيز)، Revolut/Monzo (وضوح مالي)، Duolingo (Streak/XP بلطف)، Notion (بساطة).

## 12. UX شاشة بشاشة (Screen-by-Screen)

> لكل شاشة: الهدف، العناصر، الـ primary action، حالات خاصة.

**Splash** — هوية + تحميل DB محلي. لا نصوص كثيرة.

**Intro ×3** — (1) "ما تعرف وين راحت فلوسك؟" (2) "لا تكتب — إحنا نفهمها لك" (3) "وفّر وكأنها لعبة" (تظهر الخزنة). primary: التالي / تخطّي.

**Country & Currency** — قائمة دول مع أعلام + عملة افتراضية. primary: متابعة.

**Privacy** — 4 رسائل ثقة (on-device / صلاحيات محدودة / لا بيع بيانات / حذف فوري). primary: فهمت، متابعة.

**Permissions / Method**
- Android: شرح ثم زر "السماح بقراءة رسائل البنك" + "لاحقاً".
- iOS: بطاقات: Share Extension / Shortcut / لصق. زر "جرّب بلصق رسالة الآن".

**First Budget (optional)** — اختيار تصنيف + مبلغ + دورية. زر "تخطّي".

**Home / Dashboard** (ترتيب إلزامي):
1. تحية + Streak 🔥 + "وفّرت هذا الشهر +1,240".
2. **الخزنة 3D** للهدف النشط + النسبة.
3. **Insight ذكي** واحد (نص قصير).
4. "أين ذهبت أموالك؟" — أعلى 3 تصنيفات (bars بسيطة، لا pie).
5. آخر العمليات (3–5).
- FAB: لصق/إضافة عملية. Empty state: دعوة لالتقاط أول عملية.

**Transactions** — قائمة مجمّعة بالتاريخ، فلترة بالتصنيف/البحث، شارة "غير مؤكدة". Row: أيقونة تصنيف + متجر + مبلغ ملوّن (خصم/إيداع).

**Confirm New Transaction** (bottom sheet) — المبلغ + المتجر + التصنيف المقترح (قابل للتغيير) + التاريخ. primary: "تأكيد". secondary: "تعديل". إن جديد المتجر: hint "متجر جديد — سنتذكّره".

**Transaction Details** — كل الحقول + زر "تغيير التصنيف" (يطرح سؤال فقط-هذه/الكل) + حذف.

**Budgets** — بطاقات لكل ميزانية: المصروف/المتبقي/النسبة + Budget Bar ملوّن. تنبيهات 80/100.

**Create Budget** — تصنيف + مبلغ + دورية (يومي/أسبوعي/شهري). primary: حفظ.

**Goals** — قائمة أهداف ببطاقات خزنة مصغّرة + نسبة. FAB: هدف جديد.

**Goal Details** — خزنة 3D كبيرة + النسبة + "وفّرت X من Y" + جدول مساهمات + زر "أضف للهدف".

**Reports** — Tabs أسبوعي/شهري.
- **Weekly:** إجمالي الأسبوع + أعلى 3 تصنيفات + أعلى 3 متاجر + مقارنة بالأسبوع السابق + "أين توفّر".
- **Monthly:** نفس الفكرة بمدى شهري + اشتراكات متكررة. (Phase 2: المفصّل خلف Rewarded Ad.)

**Subscription Detector** — قائمة اشتراكات مكتشفة (Netflix, Shahid, STC Pay...) + المبلغ/الدورية + زر "ذكّرني قبل التجديد".

**Achievements / Badges** — شبكة شارات (مقفولة/مفتوحة) + المستوى الحالي + شريط XP + التحدي الأسبوعي.

**Offers & Coupons** (Phase 2) — كوبونات سياقية محترمة للخصوصية (matching محلي).

**Profile** — المستوى، Streak، إجمالي التوفير، الإنجازات.

**Settings** — العملة/الدولة، اللغة، الإشعارات، طريقة الإدخال، الثيم.

**Privacy & Data** — شرح + "تصدير بياناتي" + **"حذف كل بياناتي"** (تأكيد مزدوج).

**Manual Paste Message** — حقل لصق + معاينة قابلة للتعديل + تأكيد.

## 13. نظام التلعيب (Gamification System)

> القاعدة الذهبية: **يكافئ السلوك المالي الصحي، لا الفتح المتكرر العبثي.** لا dark patterns.

| العنصر | المنطق |
|---|---|

## 15. المعمارية التقنية (Technical Architecture)

### 15.1 الطبقات (مبدأ العزل)
```
[Input Layer]
   Android SMS BroadcastReceiver | iOS Share Extension/Shortcut | Manual Paste
        ↓ (نص خام + metadata)
[Parser Engine]      ← rule-based, مستقل تماماً عن UI، قابل للاختبار وحده
        ↓ (ParsedTransaction DTO)
[Categorization Engine]  ← keywords → merchant_map → user-learning
        ↓
[Local Database] (SQLite مشفّر)
        ↓
[Insights / Budget / Gamification Engines]
        ↓
[UI Layer] (RTL, state management)
```
**قاعدة صارمة:** الـ UI لا يستدعي Parser مباشرة. كل شيء يمر عبر use-cases/repositories. هذا يتيح اختبار المحرك بـ unit tests على آلاف الرسائل دون تشغيل واجهة.

### 15.2 توصية الـ Stack
**Flutter** (توصية أساسية): UI واحد لمنصتين، أداء عالٍ، تحكّم كامل بالـ RTL والحركة، ومجتمع جيد. (React Native بديل مقبول إن كان الفريق JS-heavy، لكن SMS/Share native modules أنضج عملياً مع Flutter platform channels.)

| المكوّن | الاختيار | السبب |
|---|---|---|
| Framework | Flutter | منصتان، RTL، motion |
| Local DB | **Drift (SQLite)** + **SQLCipher** | علاقات + تشفير at-rest |
| (بديل) | Hive/Isar | إن كان النموذج بسيطاً — لكن العلاقات هنا تفضّل SQL |
| State | Riverpod أو Bloc | عزل واختبارية |
| Android capture | BroadcastReceiver (RECEIVE_SMS) عبر platform channel | التقاط فوري |
| iOS capture | Share Extension + App Intents (Shortcuts) | قيود iOS |
| Animation/Vault | **Rive** | state-driven (امتلاء الخزنة بالنسبة) |
| Secure key store | Keychain (iOS) / Keystore (Android) | مفتاح تشفير DB |
| Local notifications | flutter_local_notifications | تنبيهات بلا سيرفر |

### 15.3 ملاحظات منصّية حرجة
- **iOS لا يقرأ SMS تلقائياً — نهائياً.** التصميم يجب أن يجعل Share/Shortcut/Paste تجربة درجة أولى لا "خطة بديلة محرجة".
- **Android RECEIVE_SMS** سياسة Google Play صارمة جداً: التطبيقات التي تطلب صلاحية SMS يجب أن يكون SMS وظيفة جوهرية ومعلنة، وقد تحتاج Declaration form. **خطر رفض النشر — يجب التحقق مبكراً** (انظر المخاطر).

## 16. استراتيجية التحليل (Parsing Strategy)

**نهج تدريجي:**
1. **Bank profiles** — لكل بنك/محفظة `parsing_rules` (regex + templates) مفتاحها `bank_key + locale`. نبدأ بأكبر مزوّدين في أسواق الإطلاق.
2. **Field extractors** — amount, currency, merchant, type, date/time, card_last4, balance_after. كل حقل extractor مستقل مع `parse_confidence`.
3. **Normalization** — توحيد اسم المتجر (إزالة لاحقات، توحيد حالة الأحرف، إزالة أرقام عشوائية) قبل ربطه بـ merchant_map.
4. **Fallback** — إن فشل profile معروف: heuristics عامة (التقاط أرقام + عملة + أكبر سلسلة أحرف لاتينية كاسم متجر) ثم حالة "pending" للمراجعة.
5. **Confidence gating** — confidence منخفض → لا تصنيف صامت، اطلب تأكيد.
6. **Telemetry بلا بيانات** — نقيس *نسبة نجاح parse لكل bank_key* (عدّاد مجهول، لا نص رسالة) لتحسين القواعد.

**خطة الاختبار:** corpus من رسائل بنكية حقيقية (مجهّلة) لكل بنك مدعوم → suite اختبارات ذهبية (golden tests) يجب أن تمر بـ ≥90% قبل أي إطلاق. أهم أصل في المشروع هو هذا الـ corpus.

**قابلية التوسّع:** القواعد قابلة للتحديث عن بُعد (config صغير) لإضافة بنوك دون تحديث متجر.

## 17. استراتيجية الخصوصية (Privacy Strategy)

| المبدأ | التنفيذ |
|---|---|
| On-device processing | كل parse/تصنيف/تخزين مالي محلي — لا يُرفع أبداً |
| backend (محدّد) | **MVP:** auth + backup مشفّر E2E (blob فقط) + مقاييس مجهولة + parsing_rules config. + (Phase 2) عروض مجهولة. **لا يستقبل بيانات مالية قابلة للقراءة — فقط blob مشفّر لا نملك مفتاحه.** |
| تشفير at-rest | SQLCipher + مفتاح في Keychain/Keystore |
| صلاحيات أدنى | SMS فقط (Android)، لا قراءة جهات اتصال/موقع بلا سبب |
| شفافية | شاشة Privacy صريحة + سياسة واضحة |
| تحكّم المستخدم | "تصدير بياناتي" + "حذف كل بياناتي" (فوري ونهائي) |
| لا بيع بيانات | التزام صريح، ونموذج الربح لا يحتاجه |
| Backup اختياري (Phase 2) | مشفّر end-to-end على iCloud/Drive، اختياري وبموافقة |
| Telemetry | عدّادات مجهّلة فقط (نجاح parse، crashes) — لا محتوى مالي، خيار opt-out |

رسائل الثقة داخل التطبيق: «بياناتك المالية تبقى على جهازك ولا تُرفع أبداً» · «نحفظ فقط بريد دخولك وإحصاءات مجهولة لتحسين التطبيق» · «نقرأ فقط الرسائل التي تسمح بها» · «لا نبيع بياناتك» · «احذف كل بياناتك متى شئت».

> **تحديث القرار النهائي (Auth في MVP + Backup اختياري):** الدخول جزء من onboarding، والـ Backup مفصول واختياري ومطفأ افتراضياً.
> **الرسالة الملزِمة (تفصل المفهومين بوضوح):** **«تسجيل الدخول لتحديد هويتك. بياناتك المالية تبقى على جهازك افتراضياً. تفعيل النسخ الاحتياطي اختياري — وعند تفعيله تكون النسخة مشفّرة end-to-end لا نقدر نقرأها. الدخول ≠ مزامنة البيانات.»**
> ⚠️ **شفافية:** بدون تفعيل الـ backup، لا تغادر أي بيانات مالية الجهاز. مع التفعيل، تغادر فقط كـ blob مشفّر E2E. الرسائل التسويقية تعكس هذا بدقة بلا مبالغة.

## 24. قواعد العمل والقرارات المحسومة (Business Rules — LOCKED)

> قرارات نهائية متفق عليها. أي تغيير لاحق يجب أن يمرّ كـ change request موثّق.

### 24.0 المصادقة (Authentication) — ✅ في MVP (مفصولة عن الـ Backup)
> 🔒 **القرار النهائي:** الدخول والـ Backup **مفهومان منفصلان**. الدخول جزء من onboarding (هوية من اليوم الأول). الـ Backup **اختياري ومطفأ افتراضياً** ويُفعَّل لاحقاً من الإعدادات.
- **طرق الدخول:** Google Sign-In + Apple Sign-In + بريد/OTP (Amazon SES).
- **توقيت الدخول:** **أثناء onboarding** (هوية المستخدم متاحة من اليوم الأول).
- **بدون backup، الدخول وحده لا يزامن بيانات مالية** — البيانات تبقى محلية فقط حتى يفعّل المستخدم الـ Backup.
- مواصفات التصميم في **docs/specs/AUTH_AND_ADMIN_SPEC.md**.

### 24.1 التخزين والـ Backup — ✅ اختياري ومطفأ افتراضياً
- **التخزين الأساسي محلي** (on-device، مشفّر) — مصدر الحقيقة دائماً الجهاز. **يعمل التطبيق بالكامل بدون تفعيل أي backup.**
- **الـ Backup السحابي المشفّر E2E: اختياري + Disabled by default.** يُفعَّل يدوياً من **Settings > Backup & Restore**.
- **عند التفعيل، التطبيق:**
  1. يشرح نموذج الخصوصية (E2E، لا نقرأ بياناتك).
  2. يولّد إعداد التشفير (مفتاح K).
  3. يطلب **passphrase** من المستخدم.
  4. يعرض **recovery code** ويُلزم المستخدم بحفظه (تأكيد).
- **التشفير E2E:** K مشتقّ من passphrase (Argon2id) + تشفير AES-256-GCM محلياً قبل الرفع. **السيرفر يحفظ blob مشفّر فقط، لا يملك K، لا يقرأ المحتوى.**
- **الاستعادة (Restore):** عند الدخول بنفس الحساب على جهاز جديد **وكان هناك backup مفعّل** → عرض **«استعادة نسختك الاحتياطية المشفّرة؟»** → إدخال passphrase/جلب K → فكّ التشفير محلياً → استرجاع كامل.
- **إن لم يُفعَّل الـ backup أبداً:** الدخول على جهاز جديد لا يسترجع شيئاً (لا توجد نسخة). هذا متوقّع ويُوضَّح للمستخدم.
- ⚠️ **تحذير الـ recovery:** فقد passphrase + recovery code = لا يمكن فكّ النسخة (E2E). يُعرض بوضوح عند التفعيل.
- **export/import يدوي مشفّر** يبقى متاحاً كبديل.

### 24.2 حذف الحساب والبيانات — ✅ في MVP
- **Soft Delete لمدة 30 يوماً:** عند طلب الحذف → يُعطَّل الحساب ويُجدوَل للحذف النهائي بعد 30 يوماً (قابل للاستعادة بالدخول خلال المدة)، وتُمسح النسخة الاحتياطية في نهاية المدة.
- البيانات المالية **المحلية** تُمسح فوراً عند الطلب.
- متوافق مع متطلبات App Store / Google Play (حذف داخل التطبيق).

### 24.3 معادلة «وفّرت هذا الشهر»
- **التعريف:** الفرق في إجمالي المصروفات بين الشهر الحالي والشهر السابق.
- **الصيغة:** `وفّرت = إجمالي مصروفات الشهر السابق − إجمالي مصروفات الشهر الحالي`.
- قيمة موجبة = وفّر (صرف أقل) → تُعرض كـ `+`. قيمة سالبة = صرف أكثر.
- **القاعدة الرسمية (Same-Period Comparison) ✅ مقفولة:** المقارنة **بنفس المدى الزمني** — مصروفات month-to-date حتى اليوم الحالي مقابل مصروفات نفس عدد الأيام من بداية الشهر السابق. هذه هي طريقة الحساب المعتمدة (لا الشهر السابق كاملاً).
- يُستثنى الدخل (type=income) من حساب المصروفات.

### 24.4 تعريف الـ Streak
- **يُحافَظ على الـ streak بـ:** مراجعة أو إضافة/تأكيد **عملية واحدة على الأقل يومياً**.
- مجرّد فتح التطبيق بلا فعل لا يكفي.
- **timezone:** Asia/Riyadh (اليوم يُحسب بحدود منتصف الليل بتوقيت الرياض).
- streak freeze: يُحدَّد عدده في جدول XP/Gamification (نوصي: واحد أسبوعي).

### 24.5 De-duplication للعمليات
- **عملية مكرّرة = نفس المبلغ + نفس المتجر + نفس الوقت ± دقيقتين.**
- عند المطابقة → تُتجاهل الرسالة المكرّرة (لا تُنشأ عملية ثانية)، مع log داخلي.

### 24.6 تجاهل الرسائل غير المالية
- **أي رسالة لا تحتوي على معاملة مالية واضحة (مبلغ + نوع عملية) تُتجاهَل بصمت.**
- يشمل: أكواد OTP البنكية، العروض الترويجية، تنبيهات الرصيد بلا عملية، الإشعارات العامة.
- لا تظهر للمستخدم ولا تُحفظ كعملية.

### 24.7 blockers تشغيلية (قبل/أثناء التطوير)
- **سياسة Google Play SMS:** تُراجَع أثناء التطوير (مع تجهيز Declaration + fallback يدوي).
- **Corpus الرسائل:** يُبنى من رسائل بنوك ومحافظ **حقيقية** (مجهّلة) **قبل** تطوير المحرك → أساس golden tests.
