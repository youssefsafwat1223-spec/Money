## 1. Executive summary

The remediation program's **security core held up under independent attack**: release fail-closed configuration, stub-auth unreachability, the local data-owner gate, Edge-Function service-role authorization, the purge saga's durable retry handle, RLS posture across all user tables, per-item iOS capture acknowledgement, and the Android durable queue were all re-verified from source (and, where possible, by executing the repo's own tests) with no bypass found. All locally runnable gates are green at this HEAD: **993 Flutter tests, 19/19 migration tests, 54 Deno tests, analyze 0 issues, migration lint PASS, iOS packaging guard PASS**.

The fresh audit nevertheless found **33 new findings (10 High, 15 Medium, 8 Low)** — including **two defects inside the remediation itself**:

1. **The MALI-027 migration pipeline's version-awareness is inert in production** (empirically proven): Drift stamps `PRAGMA user_version = schemaVersion` during connection open, *before* the pipeline's discovery phase reads it. The downgrade guard can never fire (fail-open on newer schemas), the versioned-migration forward contract will silently skip the first migration ever registered, and two version-gated column repairs are unreachable for genuine legacy databases. The 19 tests stay green only because their fixtures set `user_version` **after** open — a precondition production never has. Atomicity, rollback, integrity postflight and retry semantics are all genuinely correct; the version layer above them is decorative.
2. **The MALI-014 v3 restore's FK-suspension is a silent no-op** (`PRAGMA foreign_keys = OFF` issued *inside* the restore transaction — a documented SQLite no-op, stated in this repo's own code comments): every restore actually runs with FK enforcement ON, so backups containing active children of soft-deleted parents (deleted subscription with payments, deleted goal with contributions, deleted plan with links) or v2 backups restored to fresh installs **fail permanently with a rollback**. The rollback protects the local DB; the user's cloud copy becomes unrestorable — significant data loss after device loss.

Beyond these, the audit surfaced a **second, uncontrolled financial-aggregation tier** (Dart-side folds in feature providers that contradict the canonical repository predicate on four core screens), a **multi-device sync layer whose conflicts are terminal for most entity types** (resolver covers 4 of ~12; consecutive offline edits self-conflict; a child-pull path advances its cursor past skipped rows, permanently losing them; sign-out flushes omit child outboxes entirely), and a **cross-user residue path** (the native App Group capture queue survives sign-out and imports user A's bank messages into user B's ledger).

**Final verdict: `Ready for internal beta only`** (§30). The security floor is real and the app is safe to dogfood internally on single devices against staging — but the new High cluster (financial-surface contradictions, multi-device data loss, backup restorability, migration version-ownership) must be fixed before staged release validation, and the 12 external environment gates from the prior audit remain open on top of that.

## 6. End-to-end flow maps (deltas vs historical audit)

**Capture (iOS):** Share/App Intent → `SharedCaptureStore.enqueue` (App Group, flock, SHA-256 payload id) → app `peekPendingPayloadsJSON` (non-destructive) → per-item import (atomic tx + dedup marker + outbox) → `remove(payloadID:)` ack. The historical destructive-drain path exists but has **zero Dart call sites**. App Intent persists the payload before its first network suspension and removes only its own payload on confirmed success. *Gap: the queue is not purged on sign-out (MALI-054n §8).*

**Capture (Android):** ACTION_SEND → `DurableCaptureQueue` (SharedPreferences, synchronous enqueue in `onCreate`/`onNewIntent`, `@Synchronized`, 200-cap, corruption-safe) → Dart peek/ack. SMS receiver exists but is manifest-commented (Play-safe). *Gap: `apply()` (async) persistence would be unsafe from the receiver context once SMS ships (MALI-068n).*

**Ledger sync:** local write + outbox in one tx → push (upsert on `(user_id, client_request_id)`; conditional-update is client-side read-then-check) → pull (keyset `(updated_at,id)`, rows + cursor advanced in the same tx). *Gaps: null-base blind overwrite; consecutive-edit self-conflict with no transaction resolver (MALI-052n); withdrawal type collapses (MALI-056n).*

**Planning/children sync:** parents as ledger; children (contributions/payments/links) pulled after parents but can be **skipped while the cursor advances past them — permanent hole** (MALI-051n). Conflict resolution UI covers budgets/goals/subscriptions/plans only.

**Sign-out:** 6s best-effort push flush (accounts+planning parents+ledger only — **children omitted**, MALI-053n) → DB wipe (table coverage verified complete, §12) → owner-uid delete → best-effort device unlink. *Native capture queue and `pending_notification_actions.json` survive (MALI-054n / MALI-070n).*

**Backup/restore:** one-tx snapshot → Argon2id+AES-GCM → per-user Storage path. Restore: preflight → conditional delete → insert. *The FK-OFF pragma inside the tx is a no-op → restores run FK-ON (MALI-045n).*

**Account deletion:** in-app request → `account_purge_queue` (30-day) → cron → worker resumes at first incomplete step, storage→SQL→auth, queue row deleted only after all steps (re-verified: no failure path destroys the retry handle).

## 11. Financial-integrity assessment

The MALI-018 canonical predicate is real, correct, used by every SQL aggregate in the repository layer, and locked by an executed, passing cross-view invariant test — headline/category/merchant/daily/budget/report agree for its fixture. The systemic weakness is a **second, uncontrolled aggregation tier**: Dart-side folds in feature providers re-derive "expense" with their own status/refund/currency/period rules on at least six surfaces (transactions header, Home monthly groups, plan spend, dashboard budget rings, bill paid totals, subscriptions monthly), so a user can see three different numbers for the same month on three screens with no data corruption anywhere (MALI-047n…050n, 062n, 064n). Multi-currency discipline holds at the repo boundary but leaks wherever features sum raw amounts (plans; the PDF donut center). The dormant Supabase summary tier (0030 RPCs + `SupabaseTransactionRepository`) is a pre-MALI-018 time capsule that would reintroduce the refund/exclusion bugs the moment its flags flip (MALI-063n). Remediation frame: extend the invariant test to the provider tier, forbid `fold`-over-`amount` outside repositories, and fix-or-delete 0030 before any rollout. Money-as-REAL remains the deferred MALI-026 project; no new precision regressions were introduced.

## 12. Database and migration assessment

The MALI-027 pipeline delivers exactly what its transaction can deliver — schema, repairs, seed, backfills, unconditional FK postflight and the version bump commit-or-roll-back as one unit; memoization/retry semantics are correct. Four constructed attacks were adjudicated **not real**: exceptions from `transaction()` itself (rolls back + rethrows + memo cleared), the nested `_relaxCardsAccountNullable` savepoint (drift 2.34 nests via SAVEPOINT; nothing references `cards`), an `_initFuture` clearing race (single-isolate, synchronous clear), and FK-verification timing (per-connection, pre-txn, no in-txn toggles). The structural defect is singular and foundational: **the pipeline believes it owns `user_version` and it does not** — Drift's `DynamicVersionDelegate` rewrites it at every open (empirically proven: v10→27, v999→27), so the downgrade guard, the versioned-migration forward contract, and the v8/v9-gated repairs are all inert in production while the test suite (which injects versions post-open) stays green (MALI-046n). Until `enableMigrations: false` hands version ownership to the pipeline, real safety rests entirely on the shape-based idempotent repairs — which are strong, and the wipe/ownership layers above them (MALI-011 table coverage independently re-enumerated complete; MALI-002 gate ordering crash-safe) are the best-attacked-and-held parts of the system. Secondary: the SQLCipher key copy in `user_settings` (MALI-058n), connection leak on failed init + second same-file instance without `busy_timeout` (MALI-069n), missing `transactions(account_id)`/`(category_id)` indexes (MALI-073n).

## 13. Backup/restore assessment

The v3 snapshot design is genuinely good: one-transaction point-in-time reads; complete business-data inventory with documented exclusions **enforced by a dynamic schema guard test** (no unclassified table can ship); raw SMS excluded; Argon2id(64MB/3/2) + AES-256-GCM with password+recovery slots; in-memory build/upload (no temp files); per-user Storage path under `auth.uid()` RLS; preflight that rejects malformed/truncated/newer snapshots before any DELETE; and a test-proven single-transaction rollback that leaves the original DB intact. The one serious flaw inverts the design's intent: the restore's FK suspension is a no-op (MALI-045n), so the intended tolerance for orphaned active children and v2 dangling references silently became permanent restore failures for common data shapes. That single fix is the gate item; the key-in-backup (MALI-058n), passphrase-trim asymmetry, blob-version validation, and `hasRemoteBackup` error handling (MALI-076n) are cheap follow-ups.

## 14. Sync and multi-device assessment

Local atomicity (MALI-007) and pull pagination/cursor durability (MALI-008 core) are genuinely closed — no process-kill window was found that loses a committed local write, re-pulls a partial page, or duplicates data (idempotency keys are consistent throughout). The weak layer is **concurrency semantics**: every "conditional" write is client-side read-then-write, accounts and deletes have no guard at all, and base-token bookkeeping actively generates false conflicts on consecutive offline edits because outbox items are never re-based or coalesced. That would be tolerable if conflicts were universally resolvable — but the resolver covers 4 of ~12 conflicted entity types, making `sync_status='conflict'` a silent, permanent sync freeze for transactions, accounts, settings, and all child records (MALI-052n). Combined with the child-pull cursor-skip loss (MALI-051n), the sign-out child-flush gap (MALI-053n), and the accounts mass-rollback on default-switch (MALI-055n), a realistic two-device user **will** eventually see: an edit that never leaves device A, a payment-history hole on device B, and account fields snapping back. Fix order: (1) universal conflict resolution or explicit LWW; (2) re-base/coalesce after push; (3) park skipped child rows; (4) child outboxes in the sign-out flush; (5) server-conditional updates to close the TOCTOU (requires the version-column migration deferred from MALI-022).

## 15. Authentication and consent assessment

Genuinely fail-closed in release: config is compile-time, the runtime guard is unconditional and outside debug-only code, CI refuses empty defines in all three production workflows, and stub auth is doubly gated with no UI route to the fixed OTP. Session admission is correctly sequenced — owner verification precedes every authenticated transition, wipe-before-admit is crash-safe by key ordering, and expiry is distinguished from sign-out. Consent is architecturally sound (persisted, revocable, gated at every egress point including the native layer with fail-safe-false defaults) but **defaulted on with no onboarding opt-in** (MALI-059n) — the most likely compliance/store-review objection. Sign-out leaves two artifacts outside the wipe inventory: the pending-actions file (minor, and wrongly recorded as covered in the closure ledger) and the **native capture queue** (MALI-054n — the one cross-user path found by this audit). Release-mode behavioral proofs (guard firing, stub absence in the AOT binary, 2-user smoke incl. the no-owner upgrade variant, native-queue purge) map onto external gates 3/6/10.

## 29. Rollback and recovery considerations

- **Local DB:** the migration transaction rolls back atomically (re-verified); recovery from undecryptable/corrupt DB is delete-and-recreate with cloud sync as the recovery story — which currently has holes (MALI-051n/052n) and a restore blocker (MALI-045n); fix before relying on it.
- **Backups:** restore rollback leaves the original DB intact (test-proven) — the failure mode is *unrestorability*, not corruption.
- **Backend:** migrations are forward-only; backend compatibility must precede client rollout (unchanged); purge saga is resumable and its retry handle is deletion-safe; cron jobs individually unschedulable; Edge functions independently redeployable.
- **Client:** no rollout flags exist beyond `kUserCardsCloudV2` (compile-time) and the hardcoded-false summary flags; a staged-rollout kill-switch strategy is still absent (MALI-036 limits).
- **Version ownership caveat:** until MALI-046n is fixed, shipping a build with a *higher* schema version and then rolling back to an older build will NOT be caught by the downgrade guard on user devices — treat any schema-version bump as irreversible in the field.
